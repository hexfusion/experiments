# vllm-37581 — audio render JSON-serialization crash

Reproduce, root-cause, and fix [vllm#37581](https://github.com/vllm-project/vllm/issues/37581): `/v1/chat/completions/render` crashes with `TypeError: Object of type MultiModalKwargsItems is not JSON serializable` for at least Qwen/Qwen3-ASR-0.6B audio.

**Tracking:** [RHOAIENG-63587](https://redhat.atlassian.net/browse/RHOAIENG-63587) (parent: [RHOAIENG-63483](https://redhat.atlassian.net/browse/RHOAIENG-63483) — audio + video modality enablement for RHAISTRAT-968).

**Status:** Phases 1–2 done. **Both halves of the report are fixed in vLLM 0.21.0** against Qwen3-ASR-0.6B on T4.

## Why this matters

Without the fix, the audio path in the RHAISTRAT-968 multimodal cache-aware routing STRAT is structurally broken at the vLLM render endpoint regardless of any downstream work. Resolving this upstream unlocks audio scope for RHOAI 3.5 ship.

## Findings — 2026-05-20

Cluster run against `vllm/vllm-openai:latest` → **vLLM 0.21.0** (build `7a4b5ca9`), Qwen3-ASR-0.6B on T4 (worker4). Artifacts: `artifacts/run-2026-05-20T13-09-33Z/` (sine), `artifacts/run-2026-05-20T13-16-24Z/` (speech).

| Symptom | Reporter (vLLM 0.17.x) | Sine sample (0.21.0) | Speech sample (0.21.0) |
|---|---|---|---|
| `/v1/chat/completions/render` | 500, `TypeError: Object of type MultiModalKwargsItems is not JSON serializable` | 200, `features.kwargs_data.audio` as base64-msgpack | 200, same shape |
| `/v1/chat/completions` | 200, body `"languageassistantlanguage"` | 200, body `"language None<asr_text>"` (4 tokens — expected for a tone) | 200, body `"language English<asr_text>Hello. This is a VLLM model render test."` |

Speech fixture: espeak-ng synthesis of `"Hello, this is a vLLM audio render test."` at 16 kHz mono MP3.

**Interpretation:**
- The render-endpoint serialization crash is gone. Between 0.17.x and 0.21.0, the render path was updated to encode `kwargs_data` as msgpack-base64 rather than JSON.
- The chat-completions "junk output" is also gone: real speech round-trips to a sensible transcription with detected language. The sine-wave near-empty response was plausible no-content behavior, not the bug.
- Net: both halves of #37581 appear resolved. Outstanding action is to verify with the reporter on their DGX Spark / GB10 hardware and request close, then file a separate issue if any residual symptom is hardware-specific.

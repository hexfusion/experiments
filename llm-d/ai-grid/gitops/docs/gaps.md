# Gaps

This is the one list of known gaps in the lab installation. Other documents link here
instead of keeping their own list. Anything in the installation that a Helm chart or a
controller does not generate is a gap, and so is any certificate that is not issued and
renewed without a person. Dated documents record what was true on their date
and are not updated. Remove an entry when it is closed, and say what closed it in the
commit message.

## Certificates

### Site identities are not issued or renewed by Grid

The Grid CA (`grid-canary-ca`) and both site identities (`grid-canary-identity` on the
hub and site-d) were made by hand. The first set (2026-10-15, seven days, trust domain
`grid.local`, no organization) was replaced by hand on 2026-10-17 with certificates in
Grid's site shape: `CN` and `O` set to the site name, `spiffe://grid.internal/site/<site>`,
expiring 2027-01-15. The CA key is held on an administrator workstation. Enrollment
should issue these and the operator should renew them. Until then nothing renews
them, and each renewal is a manual change.

## GitOps ownership

### The Grid external provider has no declarative owner

The hub grid gateway sits behind the MaaS gateway as an external provider. Argo
deploys the gateway, but the MaaS inputs that register it are neither rendered by a
Helm chart nor generated by the MaaS or AI Gateway controllers. They were applied
by hand with `kubectl apply`, carry no owner reference, and nothing corrects drift:

- `ExternalProvider/grid` and `ExternalModel/qwen3-coder-30b-a3b`
- `MaaSModelRef/qwen3-coder-30b-a3b`
- `MaaSAuthPolicy/grid-canary-access` and `MaaSSubscription/grid-canary`

All are in `models-as-a-service`. `sites/dagobah/maas.yaml` records them, but no
Application applies it. The AI Gateway controller generates the `provider-grid`
Service from `ExternalProvider/grid`, so that Service is not part of this gap.

### The MaaS hop key pair has no creator

MaaS authenticates to the grid gateway with one key held as two Secrets:

| Secret | Holds | Read by |
|---|---|---|
| `models-as-a-service/grid-provider-key` | The plaintext key MaaS sends | `ExternalProvider/grid` |
| `grid/grid-maas-hop-validation` | The key's hash in `keys.yaml` | The grid gateway hop policy |

No chart, operator, or controller creates either Secret. MaaS and the gateway only
read them. Both were created by hand with `kubectl apply` on 2026-10-15. Until an
owner exists, the installer mints the key and writes both halves before the gateway
starts, and rotates both together.

### The MaaS gateway CA mount has no owner

The MaaS gateway verifies the grid gateway's service certificate with the CA in
`openshift-ingress/grid-upstream-ca`. That ConfigMap and the `istio-proxy` volume
mount on the generated MaaS gateway Deployment were added by hand
(`gatewayCAPatch` in `sites/dagobah/maas.yaml`). A gateway controller reconcile can
drop the patch.

### The hub gateway config is written by hand

The hub gateway runs the inline Praxis config in `sites/dagobah/gateway.yaml`. It
routes with `intelligent_route` and a fixed site-d endpoint, not `grid_site_route` with
the operator's serving config. Adding a site or a model means editing that string.
Moving to `grid_site_route` needs:

- the chart to render the MaaS hop check (Grid chart change: `auth.secretKeyRef`)
- a serving config for this gateway, which the hub operator cannot write yet (below)

### The site-d model is applied by hand

The site-d Qwen Deployment and Service in `grid-canary` are manual manifests, not an
LLMInferenceService or a chart. The site-d gateway itself is applied by Argo
(`site-d-grid-gateway`).

### The gateway chart defaults to pinned peer trust

`gatewayConfig.peerTrust.mode` defaults to `pin`, which ties a provider to one peer
certificate digest and breaks on every renewal. Grid sites use SPIFFE identities, so a
grid deployment of the chart should require `spiffe` rather than accept a pin.

### The root Application syncs by hand

The hub gateway Application has self-heal. The root `dagobah` Application does not,
so a change to the gateway's values reaches the cluster only after a manual root sync.

## Hub operator

- The operator looks for the gateway Service in its own namespace (`opendatahub`).
  The gateway is in `grid`, so it reports the Service as not found.
- GridNetwork `dagobah-local` has empty identity references and no gateway entries,
  so the operator renders no config for any gateway and runs SWIM without keys.
- SWIM uses the pod name as the site name, since no site name is set.

## Qualification

From the [MaaS to Grid canary](maas-grid-integration-20261015.md) and
[serving rollout](serving-rollout-20261015.md):

- Quota counters, exhaustion and 429, streaming billing, retries, revoked-key
  rejection, and an existing but unauthorized model are untested.
- Kuadrant's rate-limit service fails open. Auth fails closed.
- The internal extproc manifests accept self-signed certificates without chain
  verification.
- The site-d gateway's last hop to vLLM is plaintext HTTP.
- A real LLMInferenceService with a pinned ODH runtime, its InferencePool and EPP,
  and the resulting Grid InferenceProvider are not yet validated.
- The controller memory setting is not packaged.
